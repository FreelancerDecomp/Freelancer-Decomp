# x64 build (port-only)

The server modules also build as 64-bit Windows code, in parallel with the Win32 build. Win32
stays the retail reference: every x64 change is either the same code on Win32 or behind
`_WIN64` / `_M_IX86`, and CI checks that Win32's FLRegress and RpcCodecTest output does not
change.

```
msbuild src\Freelancer.sln -p:Configuration=Release -p:Platform=x64
```

The output goes to `bin_x64\` (`bin_x64_debug\` for Debug), next to `bin\`, so the `..\DATA`
paths resolve the same way. The server reads the development ini files from `bin\`; copy
`bin\*.ini`, `bin\*.txt` and `bin\*.fl` into `bin_x64\`.

A missing module listed in `DACOMsrv.ini` is logged and skipped, so the x64 server runs without
`rp8.dll`; the `DirectX8`, `MaterialLibrary` and `TextureLibrary` system components then fail
to load, which the server does not need.

## What differs on x64, and how the code handles it

**Struct layout.** Retail structures are 32-bit layouts: pointers are 4 bytes. On x64 they are
8, and every size and offset after a pointer moves.

- `FL_LAYOUT_ASSERT(cond, msg)` (`src/include/fl_layout.h`, force-included in every project) is
  `static_assert` on Win32 and checks nothing on x64. The retail size and offset checks use it.
  A check that holds on every platform stays a plain `static_assert`.
- `FL_LAYOUT_PAD(bytes)` sizes a padding array that brings a member to its retail size; on x64
  it is one byte.
- Data that goes over the network or to disk must not depend on the layout. The packet codecs
  write every field explicitly, and RpcCodecTest checks that the bytes match Win32.

**Pointers held in integers.** Code that keeps a pointer in an `unsigned int` uses
`std::uintptr_t`, which is `unsigned int` on Win32, so Win32 compiles to the same code (for
example `FPacketBase::MarshalPtr`).

**Handles that are addresses.** Some retail interfaces keep handle values in 32 bits, and some
implementations use an object's address as the handle: `IFileSystem` passes handles as
`unsigned long` and returns them as `int`, and ReadFile's UTF handles and mapping tokens are heap
addresses. The interfaces stay 32-bit. On x64, `HandleValue` (`src/include/handle_value.h`) gives
the module a 32-bit id for each address instead; on Win32 it is the address, as in retail. Kernel
handles (`HANDLE`) need nothing: Windows keeps their values within 32 bits. A real memory address
does widen: `IFileSystem::MapFileView` returns `std::intptr_t`, which is `int` on Win32, and its
callers keep the whole value.

**Finding truncated addresses.** With `FL_HIGH_MEMORY=1` in the environment, FLDedicated and
FLRegress reserve all free address space below 4 GB at startup (`src/include/x64_high_memory.h`),
so later allocations and file mappings land above it and a truncated address fails at once. The
x64 CI runs set it. Win32 ignores it.

**Interface offsets.** DACOM components answer `QueryInterface` from `{iid, offset}` tables and
step between an object and its interfaces by fixed byte offsets: retail's vtable-pointer
positions, 4 bytes apart. `FL_FACET_OFFSET(retail, Derived, Base)` (`src/include/facet_offset.h`)
is the retail number on Win32 and the real base-class offset on x64.

**Exported C++ names.** x64 decorates C++ names differently (`PBD` becomes `PEBD`, `QAE` becomes
`QEAA`). Modules that export through a `.def` file have a `_x64.def` beside it
(`dacom_x64.def`, `Content_x64.def`); keep the two in step.

**Inline assembly and x87.** MSVC has no inline assembly on x64 and generates no x87 code: all
floating point is SSE2. Every `__asm` block on the x64 path keeps its x86 code under
`#if defined(_M_IX86)` and has a portable version beside it:

- `src/include/x87_portable.h`: the FLD/FSTP copy (a signaling NaN comes out quiet) and the
  truncating `_ftol` conversion (NaN and overflow give `0x8000000000000000`). These are
  bit-exact.
- The packet codecs and x86math use doubles, operation for operation in the x87 order. The
  server runs the x87 at 53-bit precision (only a Direct3D device lowers it to 24-bit), where a
  rounded x87 result equals the SSE2 double result, so these match Win32 bit for bit.
- `x87_trig.h`: FSIN, FCOS, FPTAN and FPATAN use the CRT functions on x64, which can differ from
  the x87 instructions in the last bit.

Results can therefore still differ from Win32 in the last bits wherever the x87 kept a value at
extended precision, or where the trigonometry differs. The FLRegress comparison reports these.

## CI

The `Release|x64` build job and the `x64 server` job run on every pull request.

- **Required:** the x64 build, and RpcCodecTest output identical to Win32.
- **Required:** the x64 FLDedicated comes up and Microsoft's DirectPlay 8 client joins it
  (DPNetCheck).
- **Report-only:** a clean x64 FLDedicated shutdown, and FLRegress on x64 compared with Win32.
  When FLRegress crashes, the job reruns it under `cdb` and prints the stack.

**Engine handles in 32-bit fields.** Common keeps the engine's archetype and instance handles
(pointers) in `long` / `int` fields that retail declared that way, among them
`Archetype::Root::EngineIndex` and `Munition::BEAM_ARCH_INDEX` (about 225 uses). On x64 they
truncate; the first visible effect is the crash in `Archetype::Free` at shutdown. The plan is
to allocate EngBase's handles below 2 GB on x64, so they fit those fields unchanged.
