# Отклонения от оригинала

Здесь перечислено то, где порт сознательно или временно не совпадает с поведением retail-клиента, и «причуды retail», которые порт воспроизводит намеренно (на них ссылаются комментарии в `src/`). Читать вместе с [substitutions.md](substitutions.md) — там описано, что именно exe делает вместо вызова портированных модулей.

Формат записи: что делает retail (адрес в листинге) — что делает порт (файл в `src/`) — почему — условие снятия — владелец.

Закрытые записи из файла удаляются; их история лежит в git. Запись закрывается только с доказательством: файл и строка в `src/` плюс адрес листинга, которому код теперь соответствует.

Различия, вытекающие из правила «No retail ABI» (современные `std::`-контейнеры вместо VC6-узлов, размеры структур), долгом не считаются и сюда не заносятся.

## Клиент: метка Beta и экранный профайлер (CLIENT-BETA-LABEL, 2026-10-12)

Статус: ЖИВО — намеренное отклонение по прямому запросу владельца. Владелец: Giperion; freelancer.exe / Client и Common.dll / IVP. Условие снятия: только явное указание Giperion; при аудите retail, смене версии и завершении портирования запись не закрывать.

Retail в `FUN_00425080` (`0x00425080..0x00425138`) после flush сразу вызывает `EndScene` (`0x0042508f..0x0042509a`): ни надписи, ни замеров там нет.

Метка версии (`Beta 2`, `src/freelancer/Client/client_tick_profile.cpp`) закрыта define `FREELANCER_BETA_LABEL` и **по умолчанию выключена** (свойство `FreelancerBetaLabel` в `src/Freelancer.Diagnostics.props`, командная строка `/p:FreelancerBetaLabel=1`). Когда включена, порт рисует её в левом верхнем углу каждого завершаемого кадра, отступ 12 пикселей. `DrawClientTickProfile` вызывается из `EndSceneHalf` после `MaterialBatcher->FlushAll(1)` и до `Pipeline->EndScene`. Под меткой опционально выводится список времён предыдущего завершённого `TickClientFrame` (QPC, миллисекунды; время родителя включает детей): UI/Server/Game tick, Objects, Physics / hits (с подпунктами IVP simulate, PSI prepare, Sim units, Commit / hulls, Contacts / events, Move beams, Find beam hits, Dispatch hits), World / FX, Sound, Render, Present.

Профайлер включается define `FREELANCER_ENABLE_TICK_PROFILE` (по умолчанию 0; лист `src/Freelancer.Diagnostics.props`, командная строка `/p:FreelancerEnableTickProfile=1` имеет приоритет). При обоих define равных 0 `DrawClientTickProfile` ничего не рисует. Для физики добавлен port-only экспорт `PhySys::SetTickProfile` и контракт `src/include/common_tick_profile.h` (`FPhysicsTickProfile`): клиент ставит sink на время своего `Physics / hits`. Эти QPC-замеры и API есть только в порте; порядок и аргументы игровых вызовов они не меняют.

## Клиент: широкоформатные разрешения, камеры Hor+ (WIDESCREEN, 2026-10-16)

Статус: ЖИВО — намеренная port-only функция по прямому запросу владельца. Владелец: Giperion; freelancer.exe / Client. Условие снятия: только явное указание Giperion. Весь код под `FREELANCER_WIDESCREEN_SUPPORT`; сборка с `/p:FreelancerWidescreenSupport=0` (лист «Freelancer — diagnostics» → «Widescreen resolutions» = Off) даёт retail-поведение 4:3. При аудите retail не закрывать.

Retail знает только 4:3: страница настроек держит пять фиксированных разрешений (ctor `0x004a982f..0x004a98bc`) и принимает режим устройства только при `Width * 3 == Height * 4` (`FUN_004af120`); камеры хранят горизонтальный полуугол и выводят вертикальный из аспекта вьюпорта (`FUN_0040fd60`, `FUN_0040f8c0`, `FUN_00556ce0`, `FUN_0041a140`), поэтому на широком экране картинка теряет верх и низ, а интерфейс Win3D (камера `DAT_0067dbf8`) обрезается.

Порт с define:

- Камеры Hor+. Хранимый горизонтальный полуугол означает угол на 4:3 той же высоты; камера, чей вьюпорт занимает всю ширину поверхности, расширяет тангенс на `аспект поверхности / (4/3)` (`src/freelancer/Client/widescreen.h`); обратные пересчёты делят на тот же множитель. Вьюпорты-окна HUD (цель, связь, навкарта, превью) не шире поверхности и остаются на retail-математике. Letterbox сохраняет полную ширину и режет только высоту; на аспекте шире 1.85 полосы не уходят в минус.
- Интерфейс остаётся 4:3 по центру (масштаб по высоте): потребители, привязывавшие масштаб к ширине поверхности, берут `WidescreenEquivalentSurfaceWidth` (подбор шрифтов `FUN_00416110`/`FUN_00416f50` и ключ их кэша, полосы HUD `FUN_004d5410`, подписи контактов, круг руления, маркеры упреждения, бегущая строка, навкарта, курсор). Загрузочная картинка рисуется 4:3 по центру.
- Список режимов страницы настроек строится из режимов устройства: не меньше 800×600, не уже 4:3, до 24 разрешений (16 и 32 бит); выбор ключуется только шириной, на ширину остаётся одна высота — с аспектом, ближайшим к рабочему столу. Без сохранённого `[Display] size` полноэкранный старт идёт в разрешении рабочего стола.
- Угловые окна HUD у краёв экрана (как HudShift): `HUD_Status` вправо; `HUD_Target`, `HUD_ContactList`, окно связи `HUD_Receiver` влево; кнопки NeuroNet `NN_MainButton` вправо; главное меню: кнопки влево, `Version` вправо, логотип к левому краю. Мировые позиции окон не меняются: пока окно рисуется, обновляется или получает мышь (обходы Win3D в `win3d.cpp`), Win3D-камера `DAT_0067dbf8` сдвинута (`src/freelancer/Client/hud_widescreen.cpp`), так что меши, Project/Unproject и лучи мыши совпадают на любой глубине. Центрированные дети (`SpecialModeText*`, `ScaledBackground`) не сдвигаются.

Известные остатки: полноэкранные 2D-элементы помимо загрузочной картинки растягиваются; рисование внутри угловых окон, считающее пиксели от ширины поверхности без камеры, не сдвигается; порог LOD в `RendComp` (ширина вьюпорта / XScale) на широком экране выбирает чуть более грубый LOD, чем 4:3 той же высоты.

## SoundManager / SoundStreamer: Fraunhofer ACM (decode only) (SOUND-ACM-DECODE-ONLY, 2026-10-10)

Статус: ЖИВО — намеренное отклонение по прямому запросу владельца. Владелец: Giperion; SoundManager.dll / SoundStreamer.dll. Условие снятия: только явное указание Giperion; не закрывать при обычном аудите соответствия retail.

Retail при перечислении ACM-драйверов принимает только точное имя `Fraunhofer IIS MPEG Layer-3 Codec (advanced)` (`SoundManager.dll` `LAB_06ee8c60`, `SoundStreamer.dll` `LAB_06ef3f10`). Порт дополнительно принимает точное имя `... (decode only)` в обоих модулях (`src/SoundManager/SoundManager.cpp:443`, `src/SoundStreamer/SoundStreamer.cpp:92`). Причина: системный Fraunhofer ACM в современной Windows возвращает имя `(decode only)`, retail-поиск такой драйвер отвергает, хотя он декодирует игровые MP3/WAV. Выбирается первый совпавший драйвер, открытие и декодирование остаются через ACM, другие MP3-кодеки не принимаются.

## DALib: `CDPClientProxy::SendMsgs` — упрощённый цикл пакетирования

Статус: ЖИВО, `simplified`. Владелец: DALib.dll.

Retail `CDPClientProxy::SendMsgs` (`DALib.dll` `0x065c3730`) — ветвистая стейт-машина со своим путём для крупных сообщений. Порт (`src/DALib/CDPClientProxy.cpp:44`) собирает очередь в батч до `0x400` байт, сжимает его, если сжатый размер не больше исходного, и отдаёт в `CDPServer::SendTo`. Порядок отправки и решение «сжимать или нет» сохранены; обработка сообщения крупнее одного батча не портирована (сообщение больше `0x400` байт цикл не пропускает). Снимается портом `0x065c3730..0x065c3aa2` построчно.

## SoundManager: карта архетипов — линейный массив

Статус: ЖИВО, представление контейнера. Владелец: SoundManager.dll.

Retail держит карту архетипов звуков в красно-чёрном дереве (`+0xF8`); порт — массив, отсортированный по id (вставка добавляет возрастающие id, удаление сдвигает), поэтому порядок обхода и результат любого поиска совпадают с деревом (`FSoundManager::DestroyAllArchetypes`, `src/SoundManager/SoundManager.cpp:2093`, = `FUN_06ee4800`, порядок разрушения по возрастанию id). Различается только представление; условия снятия нет, пока порядок остаётся таким же.

## Screens / movie / boot splash: `movie.dll` через `GetProcAddress`

Статус: ЖИВО. Владелец: freelancer.exe / menu screens; вне задач по решению владельца.

Retail импортирует `MOVIE.DLL` статически (три `[Startup]`-ролика, `FUN_005b1300` `0x005b18c0..0x005b19bc`). Порт (`src/freelancer/Client/engine_init.cpp:265`, `PlayStartupMovies`) делает `LoadLibraryA("movie.dll")` и берёт шесть экспортов `MediaPlayer` по `GetProcAddress`, потому что `src/movie` не публикует заголовок в `src/include`; при отсутствии DLL или экспорта ролики пропускаются вместо отказа запуска. Условие снятия: заголовок `movie` в `src/include` и статический импорт, как в retail.

## `Acquire3DMathEngine`: один общий кэш вместо статиков по единицам трансляции

Статус: ЖИВО, `simplified` (трекер `0x06391cf0`). Владелец: Common.dll.

Тело retail (`0x06391cf0..0x06391d28`) не кэширует: каждый вызов строит AGGDESC, зовёт `DACOM_Acquire` и `CreateInstance`. Кэш в retail живёт на местах вызова — 25 файловых статиков по единицам трансляции. В порте 114 мест вызова ни одно не кэшировало, поэтому кэш свёрнут в одну `static`-переменную внутри `Acquire3DMathEngine` (`src/Common/common_csys.cpp:729`). Наблюдаемая разница: retail может держать до 25 ссылок на движок, порт — одну. Условие снятия: вернуть кэш на места вызова и привести тело к retail, если `CreateInstance` перестанет возвращать общий экземпляр.

## Universe: неинициализированные значения стека retail воспроизведены нулями

## FUN_00402500 aliasing: базовый Inherit ICliObj (2026-09-25, W3-A)

Статус: причуда retail, воспроизведена частично (решение владельца об UB retail, 2026-10-08). Владелец: freelancer.exe / SPACE_OBJ (`src/freelancer/Client/client_cliobj.cpp`).

Базовый `Inherit` `LAB_00406970` (`FCliObj::Inherit`, `client_cliobj.cpp:2091`) сначала копирует поля почленно (`+0x04` донора попадает в получателя), затем зовёт `FUN_00402500(&this->LodHead, Src->LodHead)` (`0x00402500..0x00402575`). Получается `*Dest == Source`: retail освобождает общую цепочку LOD донора (`0x00402510..0x00402520`) и читает освобождённые узлы (`0x00402550`, `0x00402565`) — use-after-free, исход зависит от кучи MSVCRT; получатель в любом случае остаётся с пустой цепочкой (`*Dest` = null, копии теряются), донор — с висячим указателем.

Порт (`CopyLodChain`, `client_cliobj.cpp:1464`) в единственном различающемся случае `*Dest == Source != null` цепочку не освобождает: получатель получает тот же результат (пустой), донор сохраняет живую цепочку. Остальные пути совпадают с листингом. На штатных данных сюда не доходят: `LAB_00406970` стоит в слоте 7 только у CliRoot и CliEQShield, а `inherit =` в `DATA\` есть только у `[Light]` (CliEQLight, свой `FUN_0040b0a0`, `FUN_00402500` не зовёт). Условие снятия: станет известно, что retail ни разу не доходит до `0x00406b31` с непустым `+0x04` у донора.

## PerfOptions (`FUN_005b38d0` / `FUN_005b3ec0` / `FUN_005b40f0`, BOOT, 2026-09-01)

Статус: структурные отличия без наблюдаемого эффекта; поведение опций (порядок, значения, apply-тела) совпадает с retail. Запись нужна комментариям в `perf_options.h`.
Владелец: freelancer.exe / Client. Условие снятия: нет (замена контейнера на статический массив не наблюдаема).

- **Реестр.** Retail — `std::list` из статик-инициализаторов (`FUN_005b3520`, 36 регистраторов в слотах `_initterm` XC `0x0060f000..0x006101bc`). Порт — статический массив `G_Options` (`src/freelancer/Client/perf_options.cpp:298`) в том же порядке, поэтому обход apply (`FUN_005b40f0`) и save (`FUN_005b3ec0`) совпадает. `GetPerfOptionSlot` индексирует `G_Slots` без проверки границ, как `FUN_005b3510` @ `0x005b3514`.
- **Запись опции без vtable.** Retail-объект 0x1c байт: vtable, имя, IDS-имя, IDS-описание, значение, «применённое», колбэк. Слот 0 («значение прочитано») у всех 36 опций = `0053e4a0` = `RET 4`, поэтому в порте его нет; слот 1 (apply опции либо переходник `004c7160` на колбэк `+0x18`) — поле `Apply` строки `G_Options` (`perf_options.h`, `FPerfOption`).
- **Снос реестра** `FUN_005b4050` @ `0x005b22c3` не портирован: он только освобождает кучу опций и узлов, а хвост WinMain реестр не читает (комментарий в `main.cpp:555`).
- **Retail-особенность, воспроизведённая намеренно.** `FUN_004afd80` всегда делает `default * 0.01`, даже когда в `optlist.ini` стоит индекс: `cockpit = 1` → 0.01 (порог `> 0.5` в `LAB_005b3820` даёт «выключено»), `skip_transition_scripts = 1` → 0.01 (порог `< 0.5` в `LAB_004548f0` даёт «включено»), `DIFFICULTY_SCALE = 2` → 0.02. Порт повторяет это как есть.

## Мелкие экспорты Common (2026-09-01)

Статус: отклонений нет; запись сохранена для комментариев в `src/Common/common_misc.cpp` (`ParseGUID`) и `src/Common/common_csys.cpp:387` (`RotateMatrix`).

- **`ParseGUID` (`0631b9c3`..`0631bb64`).** На `0631b9e7` retail делает `strcpy` остатка строки в стековый буфер (`[S+0x1c]`) и никогда его не читает (Data1 `[S+0x18]`, Data2 `[S+0x14]`, Data4 `[S+0xc..0x13]`, буфер пар `[S+8]`). - `ValueNum` (`0631bee0`) использует `MsvcrtAtof` (`src/Common/msvcrt_atof.cpp`) — десятичная эмуляция MSVCRT `atof`, `"0x10"` даёт 0 как в retail. `RotateMatrix` (`src/Common/common_csys.cpp:377` = `06303fe0`) идёт через матмашину.

## `Gun::get_hp_type_by_index`: ретейл читает на элемент дальше (2026-09-01)

Статус: UB retail, в порте детерминирован (решение владельца 2026-10-08 об UB ретейла); для всех определённых индексов поведение совпадает.

`Gun::get_hp_type_by_index` (`062f68c0..062f690a`) сравнивает индекс с размером вектора `HpGunTypes` через `CMP EDX,EAX / JG` (`062f68f8`), то есть принимает `Index == Count` и читает dword за концом массива. Порт (`src/Common/common_archetype_weapons.cpp:361`) для этого индекса, как и для любого другого вне диапазона, возвращает `HpTypeNone`. При пустом векторе используется таблица по умолчанию `DAT_063ecc38` (24 dword, `0 <= Index <= 0x17`) — границы совпадают. То же для `ShieldGenerator::get_hp_type_by_index` (`src/Common/common_archetype_equipment.cpp:1466`, ветка непустого вектора останавливается на `Count`). Имена перечислителей `HpAttachmentType` — не ретейловые (enum не оставляет символов в бинаре), ретейловы только значения; имена выведены из строк `hp_gun_type` загрузчика архетипов.

## Камеры: смешанное соглашение вызова в таблице камеры

Статус: retail-особенность, воспроизведена в порте.

Ретейловая vtable камеры смешивает два соглашения. Слоты `0x00..0x44` принимают `this` явным аргументом на стеке (начинаются с `MOV EAX,[ESP+4]`; подтверждено вызовом `push edi; call [ecx+0x18]` на `0x0051b431`). Слоты `0x48` (`LAB_0040f5d0`, `RET 4`, `this` не читается — единственный стековый аргумент является выходным вектором) и `0x4c` (`FUN_0040f5f0`, `RET 8`; вызов `mov ecx,this; push value; push key` на `0x0051b3fe`) — `__thiscall`. Порт объявляет первые как `DACOM_API` (stdcall), а `GetVelocity(float* Out3)` и `SetProperty(Key, Value)` — обычными виртуальными (thiscall) в `src/freelancer/Client/space_camera.h` (строки 11-13 и 44-62), реализации `FSpaceCamera::GetVelocity` (`space_camera.cpp:1058`) и переопределения 0x48/0x4c в GameCamera. ## rpclocal: кодеки проводного формата — ретейловые асимметрии, воспроизведённые намеренно

Адреса — в комментариях `src/rpclocal/rpc_wire_*.cpp`, `rpc_containers.cpp`, `rpc_transport.cpp`; здесь перечень, чтобы их никто не «чинил».

## `atoi`/`atol`/`_wtoi`: своя копия MSVCRT вместо CRT порта

> **Статус:** сознательное расхождение механизма при 1:1 результате. **Не «исправлять».** Владелец: `src/include/msvcrt_compat.h` (`MsvcrtAtoi`, `MsvcrtWtoi`).
> **Условие снятия:** нет; замена на CRT-`atoi` ломает чтение 32-битных хеш-ID.

Retail зовёт `atoi`/`atol`/`_wtoi` из системного `MSVCRT.DLL`: цикл без проверки переполнения, сумма заворачивается по модулю 2^32. Порт собирается с UCRT, где эти функции насыщают результат до `INT_MAX`/`INT_MIN`, а данные игры хранят хеш-ID десятичными числами со старшим битом (например `ship_archetype = 2806013121` превращался в `0x7fffffff`). Поэтому каждый ретейловый вызов портирован как `MsvcrtAtoi`/`MsvcrtWtoi` (семантика замерена на 32-битном `msvcrt.dll` Windows 10 19045: 2 млн случайных строк, 0 расхождений).

Остаточные отличия: ретейл спрашивает тот `msvcrt.dll`, что стоит в ОС (для старых ОС набор пробелов и юникод-цифр `_wtoi` не замерялся); `isspace`/`isdigit` порт берёт из фиксированной таблицы локали «C» (ретейл `LC_CTYPE` не меняет, на практике разницы нет).
Правило для нового кода: порт вызова `MSVCRT.DLL::atoi`/`atol`/`_wtoi`/`_wtol` пишется как `MsvcrtAtoi`/`MsvcrtWtoi`; если ретейл в этом месте зовёт другое (`strtoul`, свой парсер), переносить нужно именно это. На 2026-10-17 голых `atoi`/`atol`/`_wtoi` в `src/Content` и `src/imeui` нет; `src/RP8` на соответствие не перепроверен.

## FLServer: ссылка IRichEditOle при OnDestroy

> **Статус:** ЖИВО (различие окружения, MFC 4.2 против MFC 14; снимается не доработкой кода порта)
> **Владелец:** FLServer (`src/FLServer/FLServerView.cpp`, `CFLServerView::OnDestroy`, строки ~113-124)
> **Условие снятия:** порт линкуется с MFC, чей `CRichEditView::OnDestroy` обнуляет или сохраняет `m_lpRichEditOle`, либо с rich edit-контролом, который держит свой `IRichEditOle` живым после `Release` из MFC (как riched20 образца 2003 года). Тогда пара AddRef/Release убирается.

**Ретейл.** `CFLServerView::OnDestroy` (.text:0040e170) сначала вызывает `CRichEditView::OnDestroy`, затем `m_pDocument->GetInPlaceActiveItem(this)` через vtbl+0xb8. **Почему.** Это единственный способ сохранить ретейловый порядок вызовов с современным контролом; убрать или переставить запрос после уничтожения значило бы изменить retail.

## DALib: ответы перечисления хостов по IPv6 отбрасываются

> **Статус:** ЖИВО (различие окружения, DirectPlay 8.1 образца 2003 года против текущего dpnet.dll)
> **Владелец:** DALib (`src/DALib/CDPClient.cpp`, ветка `DPN_MSGID_ENUM_HOSTS_RESPONSE` обработчика сообщений, ~строка 384)
