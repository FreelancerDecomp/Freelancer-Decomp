# ReadFile.dll

`ReadFile.dll` — файловая подсистема игры: компонент `FileSystem` в трёх реализациях (DOS — каталог/файл Win32, UTF — архив ресурсов `.cmp/.3db/.vms/.txm/.sph…`, MEM — буфер в памяти) и компонент `SearchPath` (список корней через `;`). Почти всё чтение `DATA` идёт через неё, начиная с `DALib::OpenData`. Документ описывает контракты создания объектов и форматы; поведение отдельных функций и статусы — в decomp-tracker (листинг `EXE/Disasm/readfile.dll.txt`). Порт — `src/ReadFile/`, публичный ABI — [src/include/readfile.h](../../../src/include/readfile.h) (`IFileSystem`, `ISearchPath`, `IDataBuffer`, `FFileSystemDesc`); правила — [cross_dll_protocol.md](cross_dll_protocol.md). Официальных имён для многих слотов `IFileSystem` в бинаре нет: безымянные слоты остаются `SlotNN`.

## Регистрация

PE-экспортов нет, только `DllMain`: при attach регистрируются четыре фабрики (приоритет — как в retail): DOS-синглтон (`"FileSystem"`, `0x40000000`), пустой UTF-объект (`"FileSystem"`, `0x80000000`), MEM-фабрика (`"FileSystem"`, `0x80000000`) и `SearchPath`-фабрика (`"SearchPath"`, `0x80000000`). COManager сопоставляет имя из дескриптора и пробует фабрики по порядку, пока одна не вернёт `GR_OK`; реализацию выбирает поле `Implementation` дескриптора. IID отвечают: `1.11_IFileSystem` (DOS/UTF/MEM), `1.11_IDataBuffer` (буфер MEM и узлов UTF), `1.11_ISearchPath`, `1.11_IComponentFactory`; сравнение IID — побайтное. `DllMain` detach освобождает сохранённый `ICOManager`, `UnregisterComponent` не вызывает.

## Дескриптор `FileSystem` (`CreateInstance`)

Размер `0x30`/`0x34` (DOS, UTF) или `0x40` (MEM); `SearchPath` — `0x8` (размер + имя).

| Смещение | Поле |
|----------|------|
| `+0x00` / `+0x04` | размер / имя (`"FileSystem"`) |
| `+0x08` | реализация: `"DOS"`, `"UTF"`, `"MEM"` (NULL допустим для UTF) |
| `+0x0C` | путь |
| `+0x10…+0x24` | `CreateFile`: access (`GENERIC_READ`), share, security, disposition (`OPEN_EXISTING`), flags, template |
| `+0x28` | родитель (IFS), при открытии потомка |
| `+0x30` | идентификатор «find» (только при размере `0x34`), `0xFFFFFFFF` — нет |

`DALib::OpenData` создаёт DOS-объект на каталог данных (размер `0x34`, `"DOS"`). DOS-фабрика: каталог → новый DOS-объект (`0x170` байт); файл при `"DOS"` → `CreateFileA` (+ отображение в память); файл при другой реализации → повторный `ICOManager::CreateInstance` с `desc+0x28 = this`, где UTF-фабрика сопоставит `"UTF"`. Пустая строка пути не отвергается (отвергается только NULL): путь разрешается относительно корня DOS-объекта.

MEM (`0x40`): `desc+0x28 == 0`, имя реализации `"MEM"`; при `desc+0x3C` bit0 = 0 буфер выделяется `VirtualAlloc` размером `desc+0x38`, иначе оборачивается внешний указатель `desc+0x34`. QI отдаёт `IFileSystem` и `IDataBuffer`.

## Формат UTF-архива

Заголовок `0x38` байт: `+0x00` магия `"UTF "` (`0x20465455`), `+0x04` версия `0x101`, `+0x08` смещение дерева узлов, `+0x14` размер записи узла (`0x0C` или `0x2C`, иначе ошибка `0xFFFFFFFA`), `+0x18` смещение блока строк, `+0x24` смещение секции данных; смещения должны быть меньше размера файла, размер файла > `0x38`. Остальные поля заголовка не читаются.

- **Узел `0x2C`** (все 2557 файлов `DATA` этой установки используют именно его): `+0x00` смещение следующего соседа (связный список, ограничитель — база дерева), `+0x04` смещение имени в блоке строк, `+0x08` флаги (бит `0x10` — каталог), `+0x10` смещение первого потомка (каталог) либо данных (лист), `+0x1C` размер данных, `+0x20/+0x24/+0x28` упакованные DOS-дата/время (преобразуются `DosDateTimeToFileTime`).
- **Узел `0x0C`**: соседи — подряд идущие записи; `+0x00` бит 31 — каталог, строка = блок строк + `(значение & 0x7FFFFFFF) + 4`; `+0x04` смещение потомков/данных; `+0x08` число потомков/размер.
- Поиск по имени — `stricmp`; путь делится по `\` и `/`, ведущий разделитель пропускается; лист спуститься не позволяет. Чтение: смещение в файле = `header[+0x24] + узел.смещение_данных + позиция`.
- Записи читаются прямо из отображённого файла, дерево в память не материализуется. Дескриптор «текущего узла» (`OpenNode`) хранится в объекте; handle 0 в `Read`/`GetSize`/`Seek` означает корневой handle объекта.
- `OpenNode(".")` ищет узел с буквальным именем `"."`; если его нет, вызов проваливается и текущий узел не меняется (родителя не возвращает). Чтобы подняться, retail передаёт `".."` — вызывающие (EngBase hardpoint) обязаны делать так же.
- Вложенный клон (`CreateInstance` на уже открытом UTF-объекте) открывает поддерево по пути; он хранит родителя и самый верхний архив с `AddRef` и читает через его отображение.

## Общие правила

- **Склейка путей** (`FUN_06b75420`, нужна и DOS, и UTF `+0xA4`): абсолютный путь (ведущий `\`, `/` или `X:`) копируется как есть; иначе к корню добавляется разделитель, ведущий `.\` отбрасывается, каждый ведущий `..` убирает предыдущий компонент; при переполнении буфера — отказ. Известное UB retail: корень длиной `OutChars-1` без завершающего разделителя пишет терминатор за буфер; вызывающие порта дают буфер на байт больше.
- **Маски** для UTF-поиска: `*` — остаток шаблона, `?` — один символ, сравнение без учёта регистра, `\` ≡ `/`; шаблон без точки получает `.*`, шаблон, начинающийся с `.`, — префикс `*`, имя без точки — завершающую `.`. Таблица свёртки индексируется знаковым байтом: символы `0x80…0xFF` читают 128 байт `.data` перед таблицей, порт копирует их из PE. DOS `FindFirst` на этот сопоставитель **не** ходит: он вызывает Win32 `FindFirstFileA` по склеенному пути.
- **DOS `FindFirst` в retail сломан**: результат склейки пути проверяется «наоборот», успешная склейка даёт `-1` / `LastError 0xA1`; порт воспроизводит это. Рабочий поиск — UTF (EngBase вызывает его с маской `"*"` по узлу `Cmpnd`); он возвращает 1-based номер слота поиска, `FindNext` заполняет `WIN32_FIND_DATA` флагами узла, временем, размером и именем.
- Слоты «записи» у DOS — заглушки отказа (в retail нет импорта `WriteFile`); запись реально делает MEM (`Write` + рост буфера округляет конец вверх до 64 КБ).
- Слоты отображения в память `+0x3C/+0x40/+0x44`: для DOS это не новое `CreateFileMapping`/`MapViewOfFile`, а токен над уже существующим отображением (`protect` обязан быть `2`, `access` — `4`, иначе ошибка `5`); `+0x44` не вызывает `UnmapViewOfFile`. Для вложенного UTF токен выдаёт указатель в отображение родителя; верхний UTF — отказ.
- **`SearchPath`**: `SetPath` разбивает строку по `;` (пустые сегменты пропускаются), открывает записи справа налево; каждую запись режет по первому компоненту (`\\server\share`, `X:\dir` либо до первого разделителя), открывает его DOS-объектом, остаток — относительно него. `CreateInstance` пробует детей по порядку: начальный результат `-6`, `0` возвращается сразу, иначе — результат последнего ребёнка. `GetPath` копирует сохранённую строку (буфер `0x108`).

## Отличия порта и осознанные пробелы

- Контейнеры — `std::map`/`std::vector` вместо VC6-деревьев; MEM использует композицию `FMemDataBuffer` вместо MI-адапторов.
- UTF-аллокатор walker'а `0x0C` не воспроизводится 1:1 (форматов `0x0C` в установленных данных нет).
- Часть путей воспроизводит UB retail детерминированно (висячие токены закрытых файлов, неограниченные копии в стек, знаковое расширение `isalpha`); список по функциям — в заметках трекера.
- Урок, который стоит помнить: смена соглашения вызова интерфейса — поломка ABI для **каждого** вызывающего. Частичная пересборка (`Shading`, `freelancer`, `ReadFile` в разное время) однажды дала падение в нулевой vtable-слот, неотличимое от «слот отсутствует».
