# Thorn: сценарии `.thn`, кривые и пути

`Thorn.dll` — DACOM-компонент, который загружает сценарии сцен (`.thn`: интро меню, комнаты, катсцены),
хранит описанные в них сущности и события и проигрывает их кадр за кадром. Скрипт читает встроенная
Lua 3.2, результат хранит native C++ сцена. Рядом Thorn предоставляет параметрические кривые и
сплайн-пути. Страница нужна тому, кто работает с комнатами/интро, `IScriptEngine` или форматом `.thn`;
сам формат описан отдельно в [thorn_thn_format.md](thorn_thn_format.md).

Исходники — `src/Thorn/`; публичные контракты — `src/include/thorn_iface.h` и `thorn_controls.h`.
Статусы функций и расхождения с retail — в decomp-tracker и в разделе Thorn
[deviations.md](deviations.md). Правила для чужих интерфейсов — [cross_dll_protocol.md](cross_dll_protocol.md).

| Часть | Файлы |
|-------|-------|
| DACOM-фабрики и фасеты engine | `Thorn.cpp`, `Thorn.h` |
| Lua/native граница и описатели | `ThornLua.cpp`, `lua32/` |
| Сущности, события, воспроизведение | `ThornScene.h/.cpp` |
| Кривые и пути | `ParamCurve.cpp`, `SplinePath.cpp`, `SplineMath.h` |

## Компоненты

Фабрики регистрируются при загрузке DLL; **имя компонента** выбирает фабрику, `QueryInterface` — интерфейс уже
созданного объекта. Display-имя кривой не заменяет имя компонента в `CLSID` скрипта.

| Имя регистрации | Объект |
|-----------------|--------|
| `IScriptEngine` | Движок сцены; фасеты `IGeoTransformControl` (система координат сцены) и `IScriptControl` (воспроизведение) |
| `CatmullRomPCurve`, `ThornParamCurve`, `LinearPCurve`, `ThornLPCurve`, `SmoothPCurve`, `StepPCurve`, `RampUpPCurve`, `RampDownPCurve`, `BumpOutPCurve`, `BumpInPCurve`, `FreeFormPCurve` | Параметрическая кривая, `IParamCurve` |
| `CV_CRSplinePath`, `CV_CROrientationSplinePath` | Один объект пути: `ICRSpline`, `IMotionPath`, `IPersistString` |

`LinearPCurve` зарегистрирован дважды (обычный линейный evaluator и вариант на Hermite); порядок выбора
принадлежит реестру DACOM, вторая фабрика не мертва. Фабрики движка и сплайнов поддерживают controlling
outer и отдельный inner unknown; фабрики кривых поля агрегации дескриптора не используют. Внутренний
дескриптор `FThornAggDesc14` (`Thorn.h`) — не то же самое, что дескриптор с IID: по совпадению размера
их подменять нельзя.

Кто пользуется: `Common` создаёт `IScriptEngine` через DACOM и передаёт ему файловую систему; `RoomData`
(`src/Common/common_roomdata.cpp`) вытаскивает описатели и свойства для построения комнаты и освобождает
движок. Клиентский script object (`src/freelancer/Client/gf_script_object.cpp`, `gf_script_spawn.cpp`)
удерживает движок, создаёт внешние объекты по описателям, связывает их с сущностями и передаёт время.

## Lua 3.2 и загрузка

В `src/Thorn/lua32/` лежит Lua 3.2.2 (происхождение и локальные правки — `ORIGIN.txt`, лицензия —
`COPYRIGHT`); `_VERSION` — `"Lua 3.2"`, версия формата байткода `0x32`. Замена на Lua 4/5 потребовала бы
менять и API, и формат. Открыты базовая библиотека, math и I/O; строковая библиотека целиком не открывается
(в сборку входит только ради вспомогательных функций I/O). Текстовый парсер — тот же файл, что в
`luaprofile` (`lparser_stub.c` включает `luaprofile/lua32/src/lparser.c`), но VM и состояние у Thorn
своё: `ILua` из luaprofile Thorn не использует. `IProfileParser` (INI) в `.thn` тоже не участвует.

Граница Lua и C++:

- `.thn` читается через `IFileSystem` и исполняется как Lua chunk (первый байт ESC — байткод, иначе текст).
  Чанк обязан сформировать таблицу `entities`; `events` может отсутствовать; длительность берётся из
  `duration`. После исполнения загрузчик обходит `entities`, затем `events` через `foreach`, создаёт
  native сущности и по именам из событий находит их handles. Lua хранит только описание входа; сцена,
  дескрипторы событий и контроль внешних объектов принадлежат C++.
- Воспроизведение выполняют native события и контроллеры; обычный шаг не исполняет Lua chunk заново.
  Сохранение сцены пишет текст Lua из native состояния (байткод не компилируется).
- **Одна общая VM на модуль**, не отдельная на файл или `IScriptEngine`. API Lua 3.2 работает через
  глобально выбранный `lua_state`; объект загрузчика выбирает VM при создании и возвращает прежнее
  значение при разрушении. Текущий engine, COM-контекст, сцена, handle обрабатываемой сущности и таблица
  имён→handles — модульное состояние, заимствованное без `AddRef`/`Release`. Загрузка поэтому не
  транзакция: вложенная загрузка из tag method подменяет эти значения, и одновременная работа нескольких
  потоков с одной VM не поддерживается.
- `lua_Object` — handle C API, а не указатель; временные handles живут между `lua_beginblock` /
  `lua_endblock`. Строка из Lua принадлежит VM, долгоживущую копию нужно делать. Чтение таблицы может
  вызвать tag method и GC. Ошибки VM идут через `setjmp`/`longjmp`, деструкторы C++ при таком переходе не
  вызываются.
- Время: в `.thn` секунды, внутри сцены и расписания — целые миллисекунды. Имена из Lua заимствуются на время
  вызова фабрики, фабрика копирует их.

## Сцена, события, владение

`FScriptEngine` владеет `FThornScene`: реестром сущностей и master-коллекцией событий. Pending и active
события хранят заимствованные ссылки, stop times владеют отдельные узлы времени; порядок active учитывает
зависимости между сущностями. Callback может менять сцену во время обхода, поэтому выбранный узел, его
payload и сохранённый receiver имеют разный срок жизни — повторный поиск по ключу после callback не
заменяет чтение выбранного узла. Остановка и повторный запуск сохраняют загруженную сцену, полная очистка
уничтожает события и сущности; пауза, сброс и цикл — отдельные переходы состояния.

Конкретный тип владельца описателя (`DescriptorOwnerType`) остаётся тем, что установили при создании, даже
если публичное поле `Snap.Type` меняется при применении описателя. Пакеты описателей инициализируются до
разбора Lua-полей (содержимое неинициализированной retail-кучи в контракт не входит). Поле USER передаётся
контексту без интерпретации. PATH_MOTION публикует живой `FThornPathEventDesc`; загрузчик, воспроизведение
и сериализатор работают с одним владельцем этих полей.

### Привязка сущностей (binding)

Binding связывает созданную скриптом сущность с объектом DACOM, предоставленным клиентом.
`FThornScene::Attach` находит сущность и запрашивает нужные контролы (`thorn_controls.h`) через
`QueryInterface`; события читают сохранённые QI-ссылки. Сырой `EngineObj` их не заменяет и `AddRef` только
из-за `Attach` не получает. Набор контролов выбирается по `DescriptorOwnerType`. Повторный bind освобождает
прежнюю ссылку непосредственно перед QI; ссылки принадлежат сущности; bind может быть частичным (один
контрол есть, остальных нет).

- `ATTACH_ENTITY` меняет связь и относительный transform уже существующих сущностей;
  `CONNECT_HARDPOINTS` передаёт имена двух hardpoint через compound-контрол. Это разные контракты
  (`parent_hardpoint` принадлежит CONNECT).
- `Detach` выполняет конкретный unbind; `Attach(null)` его не заменяет. Unbind и удаление сущности — разные
  последовательности очистки (unbind CAMERA/MONITOR снимает взаимные связи мониторов, удаление отдельно
  владеет локальными узлами); деструктор — не повторный `Detach`.
- Система координат сцены — живой владелец, на который сущности и события держат заимствованные ссылки;
  она отличается от geo-контрола внешнего объекта. Geo- и script-фасеты `FScriptEngine` имеют общую
  identity, но не взаимозаменяемы.

## Кривые и пути

`FParamCurve` (`ParamCurve.cpp`) объединяет семейства кривых и выбирает evaluator и политику перестройки
через `FCurveSpec`: Catmull-Rom и линейная интерполяция — свои evaluators; Smooth, Step, Ramp, Bump, FreeForm
— Hermite-данные; `ThornParamCurve` и `ThornLPCurve` меняют политику перестройки, а не полином. Данные кривой
лежат в трёх разных местах: карта по знаковому ID (`FParamKeyStorage`), список ключей для обхода и
сортировки (`EvaluationKeys_`) и производные Hermite-узлы (`Knots_`); сводить их к одному массиву нельзя
без проверки порядка публикации и удаления. Период wrapping задаёт вызывающее событие, не кривая. Публичный
результат — `float`; внутри порта значение между вычислением и потребителем передаётся как расширенный
(`FThornExtendedProgress`) — это внутренний контракт порта, не раскладка retail-объекта.

`FSplinePath` (`SplinePath.cpp`) хранит контрольные точки отдельно от ghost points, таблиц выборки и
ориентационных данных; смена точек или режима OPEN/CLOSED требует согласованной перестройки. `IMotionPath`
читает путь, `IPersistString` загружает и сохраняет его строковую форму — оба фасета одного владельца.
Сущность MOTION_PATH отдельно хранит сохранённый persist-описатель и runtime-ссылку `IMotionPath`: объединять
их нельзя, у них разные пути QI и разный срок жизни.

## Известные ограничения

- Состояние каждой функции (verified / partial / simplified) и точные арифметические термы — в карточках
  decomp-tracker (`thorn.dll`).
- Поставляемые игровые `.thn` (1423 файла в `DATA/SCRIPTS`) — байткод (`ESC Lua 0x32`); текстовый путь
  парсера проверяется сохранением сцены и повторной загрузкой.
