# CRT/STL: совместимость поведения с retail

Retail-бинарники 2003 года линкуются с системными `MSVCRT.DLL`, `MSVCP60.DLL`,
`CRTDLL.DLL` (VC6) либо содержат статически скомпилированную STL VC6. Порт собирается
современным MSVC и использует UCRT и современную STL. Одноимённые вызовы
не всегда ведут себя одинаково: меняются разбор и печать чисел, округление, ёмкость
контейнеров, маршрут отказа `operator new`, валидация аргументов, locale-таблицы.
Там, где игровое значение (hash-ID, текст на HUD, строковый ключ Lua) зависит от
такого поведения, порт воспроизводит контракт retail **поведением**, а не ABI.

Это не возврат к VC6 ABI. Бинарная совместимость с retail-DLL не цель:
раскладки `std::string`, vtable потоков, COW-счётчики и приватные методы MSVCP60
не воспроизводятся; между нашими DLL работает современная STL.

## Модули

| Что | Где |
|---|---|
| `MsvcrtAtoi`, `MsvcrtWtoi` (+ `MsvcrtWideCharToDigit`, `MsvcrtIsWideSpace`) | `src/include/msvcrt_compat.h` |
| `MsvcrtAtof` (десятичная ветка, целочисленная мантисса) | `src/Common/msvcrt_atof.h/.cpp` |
| `MsvcrtLegacyVsnprintf`, `MsvcrtFormatLuaNumber`, `MsvcrtNumericVsnprintf` | `src/include/msvcrt_numeric_format.h` |

Потребители: `MsvcrtAtoi` — все прямые десятичные разборы целых в игровых исходниках
(правило проекта: `atoi`/`std::atoi` запрещены); `MsvcrtAtof` — Common `ValueNum`,
десятичная ветка `ParseNumber`, BINI string → float; `MsvcrtFormatLuaNumber` — `luaV_tostring`
в Thorn и luaprofile (`lvm.c`); `MsvcrtNumericVsnprintf` — `NumberStringChild::Printf` /
`FormatFloat` (`font_string.cpp`).

## Реализованные контракты

- **`atoi`/`atol`/`_wtoi`**: цикл `total = 10*total + digit` без проверки переполнения,
  результат заворачивается по модулю 2^32; UCRT насыщает до `INT_MAX`/`INT_MIN`.
  Данные хранят 32-битные hash-ID в десятичной записи (`ship_archetype = 2806013121`,
  hash-ID целей миссии в сохранениях через `%u`). Насыщение ломает их и даже проверки
  «ноль / не ноль». Пробелы для `atoi` — ровно `0x09..0x0d`, `0x20`; для `_wtoi` —
  набор из `MsvcrtIsWideSpace`; цифры `_wtoi` — 18 десятичных блоков Unicode
  (`_wchartodigit`). Таблицы явные, не зависят от locale процесса.
- **`atof` (Common)**: старая грамматика — `0x10`, `0x1p+2`, `inf`, `nan` дают 0 и
  останавливают разбор; современный разбор принимает hex и бесконечности. Реализация:
  до 24 входных цифр, десятичные степени с расширенной мантиссой, округление перед
  `double`, знак нуля, диапазон и `errno`; не зависит от точности x87. Таблицы степеней
  и конверсия subnormal сверены с `_ld12tod` системного MSVCRT.
  `ParseNumber` имеет собственный base-N разбор — целиком заменять его `strtod` нельзя.
- **Lua number → string** (`sprintf("%.16g")`): старый CRT даёт трёхзначный exponent
  (`1e+020`), `1.#INF`/`1.#QNAN`, прежнее округление 17 → 16 цифр. Одних legacy-опций
  stdio недостаточно (на случайной выборке 14 888 отличий), поэтому форматтер строит
  17 цифр через `_ecvt_s`, округляет вручную и печатает по правилам `%g`.
  Lexer и `luaO_str2d` Lua разбирают литералы собственным циклом: риск `strtod`
  на них не распространяется.
- **HUD `%.Nf` с литеральным суффиксом**: половинные значения округляются «от нуля»
  (`sprintf("%.0f", 2.5)` = `"3"`, UCRT даёт `"2"`; `%.1f` от 1.25 = `1.3` против `1.2`),
  значащие цифры и дополнение нулями — прежние. Покрыт одиночный `%.Nf`, N <= 100;
  остальные форматы идут через локальную legacy-политику UCRT (`_CRT_INTERNAL_PRINTF_LEGACY_*`)
  без обещания полной совместимости произвольного `printf`.

Измеренное покрытие (`crt_numeric_regression`, `Release|Win32`): 20 025 сравнений `atof`
(биты `double` и `errno`), 300 009 случаев Lua-форматтера, 2 988 419 случаев HUD-форматирования,
41 случай ограниченного буфера; 0 отличий. Это конечные выборки, не доказательство
для всех входов.

## Известные различия UCRT / MSVCRT (измерены)

| Случай | MSVCRT (retail) | UCRT |
|---|---|---|
| `atoi("2806013121")` | -1488954175 | 2147483647 |
| `atof("0x10")`, `atof("inf")` | 0 | 16, Inf |
| `sscanf("1e+", "%lf", &d)` | 1, пишет 1.0 | EOF, ничего не пишет |
| `sprintf("%.0f", 2.5)`, `"%.1f"` от 1.25 | `3`, `1.3` | `2`, `1.2` |
| `sprintf("%.16g", 1e20)` | `1e+020` | `1e+20` |
| Inf/NaN в `%g` | `1.#INF` / `1.#QNAN` | `inf` / `nan` |
| `strtoul("-4294967297", 0, 10)` | 1, ERANGE | 4294967295, ERANGE |
| `operator new(SIZE_MAX)` | null | `std::bad_alloc` |
| `_stricmp("a","z")` | -1 | -25 (знак совпадает) |
| `iswspace(U+0085)`, `iswcntrl(U+00AD)` | false | true |
| `iswctype` | отличия по маскам на U+00AA/B5/BA, U+0085, U+00AD, U+0009/A0 | — |
| `strftime("%c")` в C locale | `06/06/24 08:02:03` | `Thu Jun  6 08:02:03 2024` |
| `acos(0.5)` (scalar-экспорт) | на 1 ULP другой | — |
| `pow(NaN, 0)` | NaN, `EDOM` | 1, `errno` = 0 |
| `localtime` < 0 | NULL, `errno` не задан | NULL, `EINVAL` |
| `_ftol` / преобразование вне диапазона | младшие 32 бита (4294967296 → 0) | `0x80000000` |
| `clearfp` | не возвращает SSE-флаги | возвращает нормализованный статус |

Совпадения (различий не найдено, менять нельзя): `rand`/`srand` (4 seed x 100 000 значений),
`strtol` для допустимых строк, `isalnum`/`isalpha`/`isdigit`/`isspace`/`isxdigit`/`tolower`/`toupper`
в C locale, `iswspace` кроме U+0085, `memcmp`/`strcmp` по знаку, `qsort` (127 массивов),
`calloc` (ошибка при переполнении у обеих сторон), `_snprintf` (return и байты при count 0..6).
Замена `rand` на `mt19937` или `sscanf("%d")` на `strtol` — уже другой механизм.

## STL и внутренние контракты

Для статически скомпилированной STL и MSVCP60 сравнивались выбранные тела с raw PE и
современный `std::`. Выводы, важные для сопровождения:

- **Рост `vector<T>`**: retail берёт `size + max(size, 1)`, современный STL — `max(new, cap + cap/2)`.
  Содержимое и self-alias вставка совпадают, ёмкость и размер запроса к аллокатору — нет.
  Ёмкость сама по себе игровую логику не меняет; код, зависящий от адреса `c_str()`/`data()`
  после роста, надо проверять отдельно.
- **Отказ выделения**: retail `operator new` возвращает null (MSVCRT), современный бросает
  `bad_alloc`. VC6 `string::_Grow` при исключении повторяет выделение с `(request+2)*width`.
  Retail-вектор с пустым состоянием и null от аллокатора пропускает store и оставляет неверные
  границы; копировать это повреждённое состояние как «контракт» не следует. Любая другая
  политика отказа — осознанная девиация, а не молчаливая замена.
- **`filebuf::setbuf`**: `setbuf(nullptr, 0)` у retail возвращает null с `EINVAL` (режим `_IOFBF`),
  современный возвращает `this` (небуферизованный); `setbuf(buf, 16)` у retail сохраняет
  владение заимствованным `FILE`, современный закрывает его в деструкторе;
  `setbuf(buf, 1)` вызывает invalid-parameter handler (по умолчанию — завершение процесса).
- **Импортируемые данные**: `npos`, `_Nullstr` — числовой sentinel совпадает, адрес пустой строки
  у современной STL другой (это хранение строки, не дефект).
- **Исключения**: конструкторы, копирование и деструкторы `logic_error`/`runtime_error`/`out_of_range`,
  MSVCRT `exception`, `_Xran`/`_Xlen`, RTTI-приведения и `type_info`, `CxxFrameHandler`,
  `except_handler3`, `_EH_prolog`, `_CxxThrowException` — на выбранных областях расхождений
  поведения не найдено.
- **Потоки**: виртуальные слоты streambuf/filebuf (`overflow`, `underflow`, `xsgetn`, `xsputn`,
  `sync`...) на выбранных сценариях совпали; печать `float`/`double` через `ostream` меняет
  только текстовый dump, но не двоичные сетевые пакеты. Раскладки vbtable различаются
  (смещение 88 против 104) — игрового значения у этого нет, ABI не предполагается.
- **Время**: `time`, `_ftime`, `clock`, `_strdate`, `_strtime` совпали; `_daylight` после `_tzset`
  у старой стороны — код зоны, а не булево значение (булева семантика совпадает).

## Открытые потребительские дефекты на момент аудита

Список — подсказка для сверки с трекером, а не источник статусов; актуальное состояние
в `decomp-tracker` и `deviations.md`.

- `RichTextEditWin::OnChar` (`0057ceb0`): UCRT `iswcntrl(U+00AD)` истинно, retail идёт дальше к фильтру и вставке.
- `Thorn::io_date` (`06f55f30`): `strftime("%c")` по умолчанию даёт другой формат.
- Common `get_value_int` (`063107c0`): retail берёт младшие 32 бита `_ftol`, порт делает `static_cast<int>`.
- Common `FUN_06328f20` / `SplitTextAtSize`: `iswspace(U+0085)` меняет границу переноса.
- Allocation failure в декодерах rpclocal (`06da5550`, `06da7b90`); `setlocale` в Thorn принимает
  современные алиасы (`en-US`, `.UTF8`), старая сторона отказывает.
- Достижимость каждого различия в штатных данных и скриптах не доказана.

## Как это измерялось и перепроверяется

Сравнивались **два текущих runtime на одной машине**, а не CRT 2003 года: системные 32-битные
`C:\Windows\SysWOW64\msvcrt.dll` (7.0.19041.x), `msvcp60.dll`, `crtdll.dll` против MSVC 19.44 /
UCRT (`/MD`, `/arch:IA32`, `/fp:precise`). Retail PE и листинги задают только *какой* интерфейс
CRT вызывался и *какие* значения доходят до него; системный MSVCRT обновлялся вместе с Windows
и не объявляется неизменным оригиналом. Для inline-тел брался raw retail PE, а не декомпиляция:
вызовы CRT в `EXE\Disasm\*.txt` не заметны, если Ghidra не дала имя (косвенные, computed).

Метод для нового входа (функция CRT/STL, импортируемая retail-модулем):

1. Найти импорты в PE (`dumpbin -imports EXE\<mod>.dll`) и вызовы в листинге `EXE\Disasm\<mod>.txt`;
   отсутствие `XREF` в листинге не доказывает отсутствие вызова — сканировать raw-байты по IAT-слоту и thunk.
2. Написать отдельный Win32 exe (настоящий MSBuild, не `cl /Zs`), который загружает системный
   MSVCRT/MSVCP60 только как эталон и сравнивает с современной стороной на векторах: граничные значения,
   `errno`, `endptr`, состояние. Не передавать объекты одной стороны другой и не смешивать их `FILE`/кучу.
3. Разобрать конкретного потребителя в retail-листинге (адрес CALL, что происходит с результатом).
   Различие без достижимого потребителя дефектом игры не называется.
4. Если потребитель зависит от различия — завести helper в `src/include/msvcrt_*.h` (или `src/Common`),
   понизить статус функции в трекере
   на время работы, затем поднять по листингу.

Регрессионный тест числовых контрактов, разовые probe-программы и CSV/JSON реестры аудита 2026-10
в публичный репозиторий не входят.

## Нерешённое

- Охват не исчерпан: неименованные, inline и computed-вызовы CRT/STL, ~170 локальных STL-тел,
  полная locale/DBCS-поверхность, поведение при `new_handler` и реальной нехватке памяти.
- Политика invalid-parameter handler: современный CRT может завершить процесс на входах,
  которые MSVCRT молча принимал; глобально отключать проверки или переводить всё на `_s`-варианты нельзя.
- `clock` стал монотонным (QPC), `time_t` 64-битный: единицы и сериализацию надо проверять у потребителя,
  а не восстанавливать VC6 layout.
