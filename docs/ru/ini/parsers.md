# Как читаются INI-файлы

Freelancer читает конфигурацию двумя отдельными INI-парсерами: `INI_Reader` в Common (используется для всех игровых данных, `freelancer.ini`, сохранений) и DACOM `IProfileParser`, встроенный в `dacom.dll` (используется только для `DACOM.INI` / `dacomsrv.ini`). Эта страница описывает оба парсера, разрешение путей к файлам и соглашения, которыми остальные страницы этой папки описывают ключи.

Проект никогда не вызывает Win32 profile API (`GetPrivateProfileString` и родственные функции); реализаций парсера ровно две. `luaprofile.dll` реализует тот же COM-интерфейс `IProfileParser` поверх глобальных переменных Lua, но INI-читателем не является.

## Какой парсер что читает

| Парсер | Для чего используется | Где реализован |
|---|---|---|
| `INI_Reader` (текст и BINI) | `freelancer.ini`, каждый файл из его секции `[Data]`, каждый файл, найденный по имени внутри другого INI, `InitialWorld.ini`, сохранения `.fl` и файлы-шаблоны (только текст) | [common_ini.cpp](../../../src/Common/common_ini.cpp), [common_textfile.cpp](../../../src/Common/common_textfile.cpp), объявлен в [common_ini.h](../../../src/include/common_ini.h) |
| DACOM `IProfileParser` | `DACOM.INI` (клиент) и `DACOMsrv.ini` (сервер), а также модули движка, которые запрашивают у него свои секции (см. [engine-dacom.md](engine-dacom.md)) | `FIniLexer` / `FIniDatabase` в [dacom.cpp](../../../src/dacom/dacom.cpp) |

Модули, которые вообще не читают INI-файлы: ximage, x86math, ReadFile, RemoteClient, RemoteServer, RemoteCommon, rpclocal, Editor, Thorn, IVP, qhull, zlib, MemoryDiagnostics, SoundStreamer, flmaterials, imeui, movie (в их исходниках нет использования `INI_Reader` или `IProfileParser`).

Ещё два входных файла в стиле INI *не* читаются ни одним из парсеров:

* `flconfigdatabase.txt` (список аппаратных особенностей RP8, путь берётся из `[RenderPipeline] MGSDB` в `DACOM.INI`) имеет собственный закрытый парсер в `src/RP8` и собственный синтаксис.
* Файлы только для записи: клиент пишет `PerfOptions.ini`, сервер пишет сохранения `.fl`, а Content генерирует три таблицы путей (см. [data-driven-files.md](data-driven-files.md) и [saves-and-initial-world.md](saves-and-initial-world.md)).

## `INI_Reader`

### Открытие файла и определение формата

* `open(path, bFatal)` отображает файл в память. Если первые 12 байт образуют корректный заголовок `BINI` (сигнатура `BINI`, а `StringTableOffset` меньше размера файла), читатель переключается на двоичную половину; всё остальное читается как текст. Проверки расширения и отдельного вызова «открыть как текст» нет. Поле `Version` не проверяется (в retail-файлах данных там `1`).
* Файл, который не удалось открыть, возвращает `false`; при `bFatal = true` читатель сначала вызывает хостовый хук фатальной ошибки (код ошибки 200). Каждое место вызова в порте передаёт `false`, кроме загрузчика раскладки клавиш в клиенте.
* `open_memory(buffer, bytes)` открывает копию блока памяти и **всегда читает текст**; BINI-данные там никогда не распознаются. Используется для содержимого сохранений/шаблонов `.fl` после их декодирования (см. [saves-and-initial-world.md](saves-and-initial-world.md)). Нулевой буфер или нулевая длина возвращают `false`.
* Один объект читателя можно перемотать с помощью `reset()`, искать в нём с помощью `find_header(name)` (который сначала перематывает), а его позицию можно сохранять и восстанавливать с помощью `get_state` / `set_state`. Серверный код использует последнее, чтобы найти в сохранении `[Time]` и затем продолжить с прежнего места.
* Во всём наборе данных 1251 из 1252 INI-файлов в retail-папке `DATA` — BINI; текстовый только `InitialWorld.ini`. `DATA` не входит в этот репозиторий.

### Модель итерации

Каждая функция чтения в проекте имеет одну и ту же форму:

```
INI_Reader Reader;
if (Reader.open(Path, false))
    while (Reader.read_header())          // next [Section]
        if (Reader.is_header("Name"))
            while (Reader.read_value())   // next key = value line of this section
                if (Reader.is_value("key"))
                    ... Reader.get_value_*(index) ...
```

* `read_header()` переходит к следующей секции и возвращает `false` в конце файла. Значения предыдущей секции, которые не были прочитаны, пропускаются.
* `read_value()` переходит к следующему ключу текущей секции и возвращает `false`, когда секция заканчивается. В текстовом режиме секция заканчивается на следующей строке, первый непробельный символ которой — `[`; эта строка остаётся для следующего `read_header()`.
* Некоторые читатели вообще не проверяют имя секции или ключа и читают **позиционно**: «первая строка значения — X, вторая — Y». Такие места отмечены на страницах отдельных файлов (например, блоки `[Group]` в `InitialWorld.ini`).
* Сопоставление через `is_header` / `is_value` **не зависит от регистра** (`stricmp` DACOM). Повторяющиеся секции и повторяющиеся ключи выдаются все, в порядке следования в файле; перекрывает ли более позднее значение более раннее или они накапливаются — решает каждый читатель, это отмечено на странице соответствующего файла. Встроенного механизма значений по умолчанию нет: «по умолчанию при отсутствии» означает то, чем была инициализирована переменная-приёмник.
* Ключи, которые не распознаёт ни один читатель, в большинстве читателей молча игнорируются (некоторые пишут в лог «unknown ini parameter», что вырезано в retail-бинарнике и в порте).

### Грамматика текста

| Элемент | Правило |
|---|---|
| Конец строки | `\n`, `\r`, `\r\n` или `\n\r`. Строка читается окном не более 1023 байт; более длинная строка разбивается, а остаток считается следующей строкой. |
| Пробельные символы | Пропускаются или обрезаются только пробел и табуляция. |
| Секция | Строка, первый непробельный символ которой — `[`. Имя — всё до первого `]` (конечные пробелы обрезаются); всё после `]` в строке игнорируется. Секция, имя которой начинается с `;` (например, `[;TextureLibrary]`), считается закомментированной и пропускается. Строки до первой секции игнорируются. |
| Ключ / значение | `name = params`. Имя идёт до первого `=` или `;` и обрезается, поэтому имена могут содержать пробелы (`data path`). Строка параметров — всё после `=` до первого `;`, с обрезанными начальными и конечными пробелами. Строка без `=` — это ключ с пустыми параметрами (так dev-`freelancer.ini` пишет `bases`, а шаблоны `.fl` — `%%PACKAGE%%`). |
| Комментарии | `;` начинает комментарий: в начале строки (после пробелов) или после значения. Поскольку `;` завершает строку параметров, значение никогда не может содержать `;`. Синтаксиса комментариев `//` или `/* */` в парсере нет (загрузчики `.fl` добавляют собственный псевдоблочный комментарий, см. страницу сохранений). |
| Кавычки, экранирование, продолжение строки | Нет. Кавычки — обычные символы (единственное исключение — символьный литерал при разборе чисел, ниже). |
| `@include` | **Не поддерживается** в `INI_Reader`. Есть только в парсере DACOM. |
| Максимальные размеры | Имя секции, имя ключа и строка параметров хранятся каждая в буфере 0x400 байт. |

### Параметры и геттеры

Параметры разделяются запятыми; геттеры принимают нумерацию с нуля. Начальные и конечные пробелы каждого поля обрезаются. Отсутствующее поле даёт `""` / `0` / `0.0` (текст) — в режиме BINI отсутствующее поле дополнительно показывает `MessageBox` с заголовком «ERROR» («header [..] value .. missing parameter N») и затем возвращает то же нейтральное значение.

| Вызов | Текстовый файл | BINI-файл |
|---|---|---|
| `get_num_parameters()` | 0 для пустой строки параметров, иначе 1 + число запятых | сохранённое число параметров |
| `is_value_empty(i)` | поле `i` пусто или отсутствует | нет значения или `i` вне диапазона |
| `get_value_string(i)` | поле `i` как текст | параметр `i`, отформатированный как текст (int как `%d`, float как `%g`) |
| `get_value_string()` | вся строка параметров | все параметры, объединённые через `", "` |
| `get_value_int(i)` | MSVCRT `atoi` от поля | байт/int как есть, float усекается, строка через `atoi` |
| `get_value_float(i)` / `value_num(i)` | `ParseNumber` от поля (ниже), возвращается как `double` | байт/int/float преобразуются, строка через `atof` |
| `get_value_bool(i)` | см. ниже | байт/int ненулевое, float ненулевой, строка `true`/`false`, иначе `atoi != 0` |
| `get_value_wstring()` | вся строка параметров, расширенная через `mbstowcs` | объединённые параметры, расширенные |
| `get_vector()` | `get_value_float(0..2)` | то же |
| `get_line_ptr()` | `"key = params"` | `"key = joined params"` |

Примечания:

* `get_value_string` возвращает указатель на общий статический буфер; вызывающая сторона должна скопировать значение до следующего вызова геттера. На это опираются несколько читателей (например, читатель `[Error] log` сначала копирует имя).
* `get_value_int` использует `atoi`, который **оборачивается по модулю 2^32**, как MSVCRT 2003 года, так что хэшированные ID, записанные большими десятичными числами (например, `2926089285`), корректно попадают в `unsigned int`. Он не понимает hex (`0x10` читается как 0) и игнорирует дробную часть (`1.5` читается как 1).
* Заголовок файла BINI позволяет типизированным значениям проходить без потерь: целые, вещественные и строковые параметры хранятся со своим типом, поэтому правила разбора текстовых чисел, приведённые ниже, к данным BINI не применяются.

### Разбор чисел (текст)

`get_value_float` / `value_num` пропускают поле через `ParseNumber`:

* Необязательный `+`, затем необязательный `-`.
* Префикс `0x`/`0X`: шестнадцатеричное число, при желании с дробной частью после `.`.
* `'c'`: символьный литерал, значение — код символа (знак игнорируется).
* Завершающая `d` (десятичное) или `b` (двоичное) после последовательности цифр, либо одна hex-цифра с последующей строчной `h`, выбирает другую систему счисления. Иначе поле разбирается как десятичное числом C `atof`, поэтому `.5`, `-2` и `1e3` работают.
* Цифры вне диапазона для выбранной системы счисления дают предупреждение и останавливают разбор.

Отдельная функция `ValueNum(text, index)` в том же файле отличается: она использует обычный `atof` (поэтому `0x10` читается как 0). Код читателей, которому нужно поведение `ParseNumber`, идёт через `INI_Reader::get_value_float`.

### Разбор булевых значений (текст)

`get_value_bool` принимает ровно `true` или `1` (истина) и `false` или `0` (ложь) без учёта регистра. Любое другое слово (`yes`, `on`, пустое) пишет через обработчик ошибок «Invalid bool value ... in .ini file» и возвращает `false`. Поэтому булев ключ без значения — это `false` плюс строка ошибки.

### Известные опасности

* Общие буферы retail имеют фиксированный размер (0x100 байт для буферов объединения и строк BINI, 0x400 для текстовых имён); retail переполняет их на очень длинных значениях. Порт увеличивает или ограничивает некоторые из них, поэтому чрезмерно длинные значения — неподдерживаемая область, а не контракт.
* У читателя BINI вызовы `is_value`, `get_name_ptr` и `get_num_parameters`, сделанные при отсутствии текущего значения (до первого `read_value` или после того, как он вернул `false`), разыменовывают null — и в retail, и в порте. Типизированные геттеры (`get_value_*`) вместо этого возвращают нейтральное значение.

## DACOM `IProfileParser`

Диспетчер компонентов DACOM владеет встроенной INI-базой. Она загружается ровно один раз при запуске, а затем запрашивается через COM-интерфейс `IProfileParser` (получаемый через `QueryInterface` у диспетчера). Модули движка используют его для чтения собственных секций `DACOM.INI`.

| Аспект | Поведение |
|---|---|
| Токены | Слова разделяются пробелом, табуляцией, CR, LF и символами `[ ] ; =`. `;` начинает комментарий до конца строки. `[`, `]`, `=` — односимвольные токены. |
| Секции | `[` слова `]`; слова объединяются одиночными пробелами. Секции хранятся отсортированными без учёта регистра. **Дублирующиеся секции сохраняются**; при поиске возвращается первая из добавленных. |
| Строки | `key = value`. Ключи и значения — фразы: слова склеиваются заново одиночными пробелами, поэтому табуляции и повторные пробелы схлопываются. Если перед `=` несколько слов, ключ — «первое слово + пробел + остальные слова». Строка без `=` хранится как голый ключ без значения (так хранятся имена DLL в `[Libraries]` и имена компонентов в `[System]`). `=` и `[` внутри значения сохраняются как текст. |
| Поиск | `OpenSection(name, 3)` возвращает handle (отвечает только значение флага 3). `GetString(handle, key, buf, n)` возвращает **первый** ключ в этой секции, равный без учёта регистра, и даёт его длину (0, если ключа нет или он пуст). `ReadLine(handle, i, buf, n)` возвращает i-ю строку (с нуля) как `key = value` или голый ключ, поэтому повторяющиеся ключи и голые строки доступны только таким способом. |
| `@include <file>` | Разбирается на месте. Относительный путь разрешается относительно каталога файла, содержащего директиву; include, который не удалось открыть, молча игнорируется. |
| Ошибки | Некорректный ввод не порождает сообщений. Строка, начинающаяся с `=` или `]`, или слишком длинная фраза, попадает в `__debugbreak()`, как в retail. Строка `key = value` до первой `[section]` разыменовывает нулевую секцию и приводит к падению, как в retail. |
| Типы значений | Парсер хранит только текст. Каждый модуль сам преобразует значения. Типичные копии вспомогательной функции принимают `true`/`yes` и `false`/`no`, считают текст, содержащий `x`, шестнадцатеричным, а в остальных случаях используют `atoi`; что принимает каждый модуль — см. [engine-dacom.md](engine-dacom.md). |

Порядок загрузки конфигурационного файла (`DALib::Startup(hwnd, iniPath)`, см. [DALib.cpp](../../../src/DALib/DALib.cpp)):

1. Явный путь приоритетен: клиент его не передаёт, сервер передаёт `DACOMsrv.ini`.
2. Иначе `DACOM.INI` в текущем рабочем каталоге, если он читается.
3. Иначе `DACOM.INI` в каталоге `DALib.dll`.

Если загрузка не удалась, запуск останавливается с «ERROR: creating DACOM with INI file». После разбора менеджер DACOM читает `[DACOM]` (`DllPath`, `IgnoreDACOMEnv`) и загружает каждую строку `[Libraries]`. Неабсолютный `DllPath` разрешается относительно каталога **исполняемого файла** (начальные `.\` и `..\` обрабатываются). Если `IgnoreDACOMEnv` не истинно (`true` или любое ненулевое число; `false` или `0` оставляет переменную окружения активной), переменная окружения `DACOM`, если она задана, заменяет `DllPath`. Полный список ключей — в [engine-dacom.md](engine-dacom.md).

## Как находятся пути к файлам

| Механизм | Что делает |
|---|---|
| Расположение конфигурационного файла | Клиент: `Freelancer.ini` в текущем рабочем каталоге (имя зашито, переопределения из командной строки в коде нет). Сервер (`FLServer.exe`): `freelancer.ini` в каталоге исполняемого файла сервера и второй файл `SrvLocal-freelancer.ini` рядом с ним, читаемый тем же читателем. Серверу одиночной игры (загружаемому в процесс клиента) передаётся путь клиента. |
| Путь к данным | `[Freelancer] data path` из `freelancer.ini` (в клиенте по умолчанию `..\Data`, в сервере ключ пишется `Data path`; ключи не зависят от регистра). `DALib::OpenData(path)` создаёт *файловую систему Data* — файловую систему DACOM с корнем в этом каталоге. Строка используется как есть (завершающий `\` обеспечивается); относительное значение поэтому интерпретируется операционной системой относительно рабочего каталога процесса. |
| `GetFileSysPath(out, rel, fs)` | Если `rel` абсолютный (начинается с `\` или имеет `:` вторым символом), он копируется без изменений. Иначе `rel` присоединяется к корню `fs`; `fs == nullptr` означает файловую систему Data. Так находится каждый файл, названный в `[Data]`. |
| `GetFullFilename(rel)` | То же присоединение к файловой системе Data, затем раскрытие до полного пути. Используется загрузчиками shape/texture-panel. |
| `OpenContentDataIni(rel, reader)` | Помощник модуля Content: корень файловой системы Data + `rel`, затем `INI_Reader::open(path, false)`. Используется загрузчиками миссий и ИИ (38 мест вызова в `src/Content`). |
| Файлы относительно вселенной | `Universe::Startup` создаёт вторую файловую систему с корнем в каталоге `universe.ini`; файлы систем, названные в `[System] file`, присоединяются к этому корню (`Systems\<Sys>\<Sys>.ini`). Прочие ссылки (файлы баз, комнат, астероидных полей ...) записываются относительно корня Data. См. [systems-and-bases.md](systems-and-bases.md) и [data-driven-files.md](data-driven-files.md). |
| Пользовательские данные | Сохранения лежат в `<My Documents>\My Games\Freelancer` (`GetUserDataPath`), локальные данные пользователя — в локальной папке данных приложений (`GetUserLocalDataPath`). |
| Рядом с исполняемым файлом | Некоторые файлы читаются из каталога запущенного исполняемого файла, а не из Data: шаблоны нового персонажа (`NewCharacter.fl`, `MPNewCharacter.fl`, `NewPlayer.fl`) и `flconfigdatabase.txt`. |

## Соглашения, используемые на других страницах

* **Таблица ключей** имеет столбцы `Ключ | Тип | По умолчанию | Значение / допустимые значения | Источник`. *Тип* — один из `string`, `int`, `float`, `bool`, `id` (строка-никнейм, которую читатель хэширует в 32-битный ID через `CreateID`, или число, используемое непосредственно как ID), `path` (имя файла относительно пути Data, если не указано иное) либо список в скобках, например `[float, float, float]`, для позиционных параметров через запятую (параметр 0, 1, 2 ...).
* *По умолчанию* — значение, которое хранит переменная-приёмник, когда ключа нет. «none» означает, что у читателя нет собственного начального значения, «не проверяется» означает, что код принимает что угодно и не проверяет диапазон и не перечисляет значения.
* «Допустимые значения» перечислены, только когда код сравнивает с фиксированным набором (цепочки `stricmp`, таблицы, enum). Если код не проверяет, на странице пишется «не проверяется», а не догадка.
* **Повторяется** означает, что ключ может встречаться в секции несколько раз и используется каждое вхождение; **побеждает последний** или **побеждает первый** пишется явно, когда более позднее или более раннее вхождение заменяет остальные.
* **Источник** — относительная ссылка на файл, содержащий читатель. Имена функций указаны, когда в файле несколько читателей.
* Примеры короткие и синтетические. Retail-папка `DATA` защищена авторским правом и не входит в репозиторий, поэтому страницы описывают форматы и ключи, а не воспроизводят данные.
* Все ключи и имена секций INI не зависят от регистра, если страница не говорит иного. Строки-никнеймы приводятся к нижнему регистру функцией `CreateID` перед хэшированием (имена длиннее 255 байт усекаются), поэтому ID, полученные из никнеймов, тоже не зависят от регистра. Прочие сравнения значений (`stricmp` или `strcmp`) отмечены там, где это важно.
