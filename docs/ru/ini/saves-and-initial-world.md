# Начальный мир, сохранения и шаблоны новых персонажей

Эти файлы хранят *состояние* игры, а не её статические данные: мир на начало игры (`InitialWorld.ini`), файлы сохранения отдельных персонажей (`*.fl`) и шаблоны, из которых генерируются новые персонажи и файлы перезапуска. Все они — **текстовый** INI (не двоичный формат BINI), читаемый через `INI_Reader`.

**Расположение файла / как он находится.**

| Файл | Где | Чем находится |
|---|---|---|
| `InitialWorld.ini` | папка Data | `freelancer.ini` `[Freelancer] initial_world` (сервер) и `[Data] Groups` (репутация); см. [freelancer-ini.md](freelancer-ini.md) |
| Сохранения персонажей `<name>.fl` | `<My Documents>\My Games\Freelancer\Accts\<папка аккаунта>\` в одиночной игре, `...\Accts\MultiPlayer\<папка аккаунта>\` для сервера мультиплеера | каждый `*.fl` в папке аккаунта — персонаж; папка аккаунта в одиночной игре — имя аккаунта, в мультиплеере — его хэш |
| `Restart.fl`, `AutoSave.fl` | та же папка | зарезервированные имена файлов (см. ниже) |
| `NewCharacter.fl` (одиночная игра), `MPNewCharacter.fl` (мультиплеер), `NewPlayer.fl` | **каталог запущенного исполняемого файла** | фиксированные имена. В папке `bin` репозитория лежат `MPNewCharacter.fl` и `NewPlayer.fl`; `NewCharacter.fl` в этой выгрузке отсутствует. |

## Формат контейнера файлов `.fl`

Файл сохранения или шаблона — одно из трёх, различаемых по первым четырём байтам (одна и та же трёхветочная проверка применяется везде, где читается файл `.fl`):

| Первые байты | Значение |
|---|---|
| `FLS1` | остаток файла — текст INI, обфусцированный фиксированным XOR, зависящим от позиции (см. [server_savefile.cpp](../../../src/Server/server_savefile.cpp)). Каждое сохранение, которое пишет игра, хранится в таком виде — и в одиночной игре, и в мультиплеере. |
| `FLSG` | отвергается: файл считается нечитаемым. |
| что угодно другое | файл — обычный текст INI с байта 0. В этой форме написаны вручную созданные шаблоны, например `MPNewCharacter.fl`. |

После декодирования текст разбирается через `INI_Reader::open_memory`, поэтому применимо всё из [parsers.md](parsers.md) (то есть файлы `.fl` никогда не бывают BINI). Ридер `[Player]` дополнительно считает имена значений `/*` и `*/` вложенной парой блочных комментариев: пока глубина больше нуля, все ключи пропускаются. Имена и описания хранятся в шестнадцатеричном виде (см. `name` ниже).

## `InitialWorld.ini`

Единственный текстовый INI в папке `DATA` retail. Он описывает мир таким, каким он бывает при старте новой игры или нового персонажа мультиплеера: группы фракций с их взаимной репутацией и то, какие джамп-гейты изначально заблокированы. В запущенной игре те же имена секций встречаются внутри файлов сохранения, потому что сохранение тоже пишется в этом формате.

Он читается в четырёх местах:

| Читает | Когда | Что читает |
|---|---|---|
| `Reputation::Startup` ([common_reputation.cpp](../../../src/Common/common_reputation.cpp)) | при запуске, из `[Data] Groups = ...` (клиент и сервер) | заголовки `[Group]`: идентичность группы и строковые ID |
| `Server_LoadWorldState` ([IServerImpl.cpp](../../../src/Server/IServerImpl.cpp)) | запуск сервера мультиплеера; в одиночной игре тот же шаг выполняется над загруженным сохранением персонажа | `[Time]`, затем `Reputation::LoadFeelings` (строки `rep` секций `[Group]`), затем открытый ридер передаётся всем контроллерам как сообщение *LoadGame* |
| Content `GameSupport` (сообщение *LoadGame*) | сразу после предыдущего | `[DynBaseInfo]`, `[locked_gates]`, `[DynSysInfo]` (см. ниже) |
| `PlayerDB::create_restart_file` ([server_classes.cpp](../../../src/Server/server_classes.cpp)) | создание `Restart.fl` | весь файл копируется дословно после шаблона `NewPlayer.fl` |

### `[Group]` (повторяется, по одной на группу фракции)

Идентичность группы читается `Reputation::Startup` **позиционно**: ридер не смотрит на имена ключей первых двух строк, а затем ожидает третью и четвёртую по имени.

| Строка (в этом порядке) | Тип | По умолчанию | Значение / допустимые значения | Источник |
|---|---|---|---|---|
| 1. `nickname` | string (не более 15 символов) | нет | Никнейм группы. Её 16-битный ID группы — CRC имени в нижнем регистре (`MakeId`), поэтому два никнейма с одинаковым CRC столкнутся. Имя ключа не проверяется. | [common_reputation.cpp](../../../src/Common/common_reputation.cpp) (`ReadGroupBlock`) |
| 2. `ids_name` | int | 0 | ID строкового ресурса с названием группы. Имя ключа не проверяется. | там же |
| 3. `ids_info` | int | 0 | ID строкового ресурса с информационной карточкой группы. Берётся, только если ключ этой строки — `ids_info`; иначе 0 (строка поглощается в любом случае). | там же |
| 4. `ids_short_name` | int | 0 | ID строкового ресурса с кратким названием. То же правило, что для `ids_info`. | там же |
| `rep` (повторяется) | `[float, string]` | нет | `rep = <feeling>, <никнейм другой группы>`: как эта группа относится к другой (знаковая доля; диапазон не проверяется). **При запуске не читается**; `LoadFeelings` читает их при загрузке мира или сохранения. Для каждой группы побеждает первый `rep` в сторону данной другой группы. Группа без строки `rep` пишет в лог «save game has corrupted reputation data». | `Reputation::LoadFeelings` |

При загрузке **сохранения** `LoadFeelings` находит каждую `[Group]` по её первой строке (снова позиционно: *первое значение блока*, каким бы ни был его ключ, является никнеймом) и затем читает только ключи `rep`. `[Group]`, чей никнейм ещё не известен, пропускается.

```ini
[Group]
nickname = grp_a
ids_name = 100001
ids_info = 100002
ids_short_name = 100003
rep = 0.5, grp_a
rep = -0.3, grp_b
```

### `[Time]`

| Ключ | Тип | По умолчанию | Значение | Источник |
|---|---|---|---|---|
| (первое значение) `seconds` | float | 0.0 | Прошедшее игровое время. Ридер берёт первое значение секции и игнорирует имя ключа. В `InitialWorld.ini` нет `[Time]`, поэтому новый мир мультиплеера начинается с 0; сохранения, записанные в одиночной игре, содержат `seconds = <float>`. | [IServerImpl.cpp](../../../src/Server/IServerImpl.cpp) |

### `[locked_gates]`

Джамп-гейты и холы, закрытые в начале игры. Читается `LoadContentGateLocks` ([SpaceSupport.cpp](../../../src/Content/SpaceSupport.cpp)) по сообщению *LoadGame*; писатель в том же файле выводит ту же секцию в сохранения.

| Ключ | Тип | По умолчанию | Значение / допустимые значения | Источник |
|---|---|---|---|---|
| `locked_gate` | id (повторяется) | нет | Хэшированный ID объекта гейта/хола, записанный десятичным числом (значения выше 2^31 — норма; завершающий комментарий `; nickname` документирует его). Блокирует гейт для игрока. | там же |
| `npc_locked_gate` | id (повторяется) | нет | То же, но блокировка относится к кораблям NPC. | там же |

### `[DynBaseInfo]` и `[DynSysInfo]`

Читаются `LoadDynBaseInfo` ([BaseDB.cpp](../../../src/Content/BaseDB.cpp)) и `LoadDynSysInfo` ([SystemInfo.cpp](../../../src/Content/SystemInfo.cpp)): ридер находит секцию, берёт первый ключ `nickname`, ищет объект и останавливается. Найденный результат не используется, и ничего в порте эти секции не пишет (соответствующие процедуры сохранения — пустые циклы, как в retail). Оба загрузчика перед просмотром перестраивают свои таблицы баз/систем из вселенной, так что секции могут отсутствовать. См. также [systems-and-bases.md](systems-and-bases.md).

## Файлы сохранения персонажей (`[Player]`)

Файл персонажа начинается с секции `[Player]`; писатель одиночной игры затем добавляет `[mPlayer]`, секции миссий, `[Time]` и блоки `[Group]`. Разбирается `PlayerData_LoadSaveRecord` ([server_savegame.cpp](../../../src/Server/server_savegame.cpp)) в запись, которая позднее копируется на живого игрока. Несколько секций `[Player]` в одном файле читаются все (значения по умолчанию на секцию сбрасываются для каждой), и побеждают последние значения. Ключи, неизвестные ридеру, пропускаются. Имена нечувствительны к регистру. Секция `[Player]` обязательна: файл без неё отвергается.

Значения по умолчанию на секцию, устанавливаемые в начале каждой `[Player]`: позиция `0,0,0`, единичная ориентация, нет системы/базы/локации, пустое описание, `money = 1968`, `interface = 3`, пустые группы оружия и таблица посещений.

|---|---|---|---|---|
| `name` | hex wide string | нет | Имя персонажа. Если текст состоит только из шестнадцатеричных цифр, он декодируется как по четыре hex-цифры на кодовую единицу UTF-16; иначе берётся как обычный многобайтовый текст. | да (hex) |
| `description` | hex wide string | пусто | Описание сохранения, в той же кодировке, что `name`. | если задано |
| `descrip_strid` | int | 0 | ID строкового ресурса, используемый вместо текстового описания. | если не ноль |
| `tstamp` | `[int, int]` | 0, 0 | Время сохранения как старшая и младшая 32-битные половины Windows FILETIME. Должны присутствовать обе, иначе обе равны 0. | да |
| `ship_archetype` | id или nickname | нет | Архетип корабля: десятичный ID, либо, если он разбирается как 0, никнейм, который хэшируется и разрешается. Загружается список групп коллизий неповреждённого корабля. Должен предшествовать `collision_group`. | да |

### Секции, которые добавляет сервер одиночной игры

Когда сервер сохраняет в одиночной игре, он записывает после `[Player]`: секции, которые каждый контроллер Content добавляет для игрока (сообщение *PlayerSave*), затем `[Time]` и блоки `[Group]` (`Reputation::Save`: строка `nickname` плюс по одной строке `rep = <feeling>, <group>` на отношение), затем вывод *SaveGame* контроллеров. При загрузке один и тот же ридер перематывается для каждого потребителя, поэтому порядок секций не важен. Секции ниже читает Content; их семантика относится к документам о миссиях ([missions.md](missions.md), [random-missions.md](random-missions.md)).

## Шаблоны новых персонажей

`PlayerData_CreateNewCharacter` ([server_savegame.cpp](../../../src/Server/server_savegame.cpp)) создаёт нового персонажа, потоково переписывая шаблон (`NewCharacter.fl` в одиночной игре, `MPNewCharacter.fl` в мультиплеере) в новый файл сохранения секция за секцией, подставляя по пути плейсхолдеры. Выходной файл называется `<хэш имени персонажа>.fl` в папке аккаунта и затем кодируется как любое сохранение. Фракция, пакет, домашняя база и пилот персонажа берутся из таблицы `NewCharDB` (см. [world-data.md](world-data.md)); если все четыре поиска не удались, файл не создаётся, а если не удались только некоторые, на выходе пустой файл и создание завершается неудачей.

* Каждая строка копируется как `key = value1, value2, ...`; строка без значения повторяет объединённый текст предыдущей строки (причуда retail).
* **Значение**, начинающееся с `%` и равное одному из плейсхолдеров ниже (без учёта регистра), заменяется; всё остальное копируется без изменений.
* **Ключ** `%%Package%%` заменяется строкой `ship_archetype` плюс по одной строке `equip` / `cargo` на каждую запись комплектации пакета.

| Плейсхолдер | Чем заменяется |
|---|---|
| `%%Name%%` | выбранное имя персонажа в hex-кодировке, как в `name` |
| `%%Faction%%` | никнейм группы репутации фракции |
| `%%Money%%` | стартовые наличные пакета |
| `%%Base_Costume%%`, `%%Comm_Costume%%` | никнеймы основного и comm-костюма пилота |
| `%%Voice%%` | никнейм голоса пилота |
| `%%Home_System%%`, `%%Home_Base%%` | никнеймы системы домашней базы и самой базы (если поиск не удался, текст плейсхолдера остаётся) |

```ini
[Player]
name = %%NAME%%
rank = 0
money = %%MONEY%%
costume = %%BASE_COSTUME%%
com_costume = %%COMM_COSTUME%%
system = %%HOME_SYSTEM%%
base = %%HOME_BASE%%
house = 0.5, grp_a
%%PACKAGE%%
```

## `Restart.fl` и `AutoSave.fl`

* `Restart.fl` создаётся в папке аккаунта `PlayerDB::create_restart_file`: декодированный шаблон `NewPlayer.fl`, за которым следует полный текст файла начального мира (`initial_world`), записанный как обычное закодированное сохранение.
* `AutoSave.fl` — имя, под которым автосохранение одиночной игры записывает текущее состояние; автосохранение мультиплеера записывает собственный файл выбранного персонажа.
* Оба имени зарезервированы: они распознаются по имени (без учёта регистра) при построении списка персонажей.

## Писатели

Единственный код, пишущий эти форматы, находится в сервере и Content: `PlayerData_SerializeToFile` ([server_pub.cpp](../../../src/Server/server_pub.cpp)) для `[Player]`, `Server_SaveSinglePlayerState` для `[Time]` и `[Group]`, процедуры `Save` контроллеров Content для остальных секций, а также `PlayerData_CreateNewCharacter` и `PlayerDB::create_restart_file` для шаблонов. Каждое сохранение сначала записывается в текстовый файл, затем перечитывается, кодируется XOR и перезаписывается с префиксом `FLS1`; если запись сообщает об ошибке, недописанный файл удаляется.
